# 深渊回响 · TS → Godot 4 + C# 迁移文档

> 目标不是「把 TS 翻译成 C#」，而是**功能等价的重写**：
> 规则一条不改，渲染、输入、资源、存档全部换成 Godot 原生能力。
> 迁移期间 TS 版原地不动当行为参照——它已于迁移完成后移除（见 Issue #81），
> 本文件保留当时的对照记录，所以正文里的 `src/**` 路径指的是历史位置。

- 引擎 / 语言：Godot **4.7.2**（.NET / Mono 版）+ **C#（net8.0）**，无一行 GDScript
- 工程位置：`godot/`（仓库里只剩这一套；TS 版已随构建流水线一并移除）
- 架构：Scene + Node + Signal + Autoload；逻辑层是**纯 C# 类**，一个 Godot 类型都不引用
- 产物：Windows `.exe` + `pck` + `data_*` 三件套，Linux 同构；CI 出 zip / tar.gz

---

## 1. 为什么逻辑层能「原样搬」

TS 版有一条从第一天就守住的红线：**`src/systems` 与 `src/core` 不 import Phaser**。
292 项测试能在 node 里直接跑，靠的就是这一点。这条红线正好是迁移的最佳切入口：

```
src/core/*     → Scripts/Core/*      纯状态与规则（Rng / Map / Entity / Game）
src/systems/*  → Scripts/Systems/*   纯规则（Battle / Skills / Affixes / Loot / …）
src/data/*     → Scripts/Data/*      数据模型 + 加载 + 校验
```

这四层在 C# 里依旧不 `using Godot`（唯一例外是 `GameDataStore` 用 `FileAccess` 读
`res://Data/game_data.json`，因为浏览器里的 `fetch` 在 Godot 里没有对应物）。
好处很直接：**headless 自检能驱动完整场战斗**，不显卡、不开窗、不需要 xvfb。

被重写的只有表现层：

```
src/scenes/*  → Scripts/Scenes/*   Phaser Scene → Godot Scene（Control / Node）
src/ui/*      → Scripts/UI/*       Canvas 绘制 → Control + StyleBox + Theme
src/main.ts   → Scenes/Boot.tscn   Phaser.Game 配置 → project.godot
```

## 3. 浏览器能力怎么处理的

| 浏览器 / Electron | TS 版用法 | Godot 版做法 |
|---|---|---|
| `fetch('game_data.json')` | 加载配置 | `FileAccess.Open("res://Data/game_data.json")`，导出后打进 pck，路径不变 |
| `localStorage` | 元进展存档 | `ConfigFile` → `user://abyss_echo_meta.cfg`（`Scripts/Autoload/GameStore.cs`） |
| `addEventListener('keydown')` | 方向键 / 数字键 | `project.godot` 里定义 InputMap（`move_*` / `interact` / `descend` / `bag`）+ `_UnhandledInput` |
| DOM / CSS 布局 | 面板与按钮 | `Control` + `VBoxContainer` / `GridContainer` + `StyleBoxFlat` + `Theme` |
| Canvas `drawImage` / `Graphics` | 房间格、图标、血条 | `Button` + `Label`（房间格）、`ProgressBar` + StyleBox（血条）、`Line2D`（连线） |
| `requestAnimationFrame` | 立绘浮动、飘字 | `Tween` / `Timer` / `_Process(delta)` |
| `setTimeout` / tween 库 | 演出节奏 | `GetTree().CreateTimer()` / `CreateTween()` |
| Electron 窗口 / 图标 / 版本号 | `electron-builder` 配置 | `project.godot` 的 `display/window` + 导出预设 `application/*` |
| `navigator` / `window` / `document` | 状态、事件 | 一律没有对应物，相关代码全部不进 C#（`Core` / `Systems` 里零引用） |

**一条必须记住的坑**：Godot 的 `Control` 在**还没进场景树**时写 `AnchorsPreset`，
只会改锚点、不会重算 offset；`SetAnchorsPreset()` 也依赖「当前父 rect」。
如果父级此刻是 0 尺寸（比如在 `_Ready` 里刚 `AddChild` 的面板），
面板会被算成 0 宽、缩在左上角。稳妥写法是**四条 anchor + 四条 offset 全部手写**。

并由自检逐条验证（见第 6 节）。

### 4.1 局内进度存档：三条离线规矩

存档这件事最容易做错的地方不是「怎么写」，而是「写了之后游戏变成什么样」。
如果存档等于「无损暂停」，它就成了作弊器。所以规则先定死，再写代码：

| 规矩 | 意思 | 落在哪 |
|---|---|---|
| 离线不推进时间 | 读档不刷新商店、不掉血也不回血、不重置冷却 | `OfflineRules`（纯函数）+ `SaveSerializer.Load` 不碰 `_shopCache` |
| 战场不存档 | 回到敌人房会重开一场新的战斗；房间的清空标记保留 | `OfflineRules` 注释里写了理由：战场中间状态的复杂度比整局高一个量级，存它等于把 `Battle` 的内部结构写进存档格式 |
| 带版本号 | 版本对不上就当没有存档，绝不在半个状态上开局 | `OfflineRules.SaveVersion` + `IsVersionSupported` |

存什么、不存什么，也是同一条判断：

- **存**：种子、楼层、周目、状态、玩家位置、血量/基础属性/金币/等级/经验、背包 id 列表、技能 id 列表、装备下标、房间的 visited/cleared 标记、运行时生成的装备（诅咒装/附魔装——它们的 id 在模板表里查不到）
- **不存**：地图、敌人、商店库存、词条视图、战斗对象。前三个由种子推导，后两个每次都要重算

落盘时机只有三个，都是「可以被打断的安全点」：下楼、战斗结算回地图、暂停菜单里保存。

## 5. 怎么跑

```bash
# 1. 拿到 Godot 4.7.x .NET 版（必须带 mono/GodotSharp）与 .NET SDK 8
#    导出模板要放到 ~/.local/share/godot/export_templates/4.7.2.stable.mono/

# 2. 逻辑自检 + 界面冒烟（都不需要显卡，CI 就跑这两个）
cd godot
dotnet build
godot --headless --path . --import
godot --headless --path . -- --selfcheck     # 36 项规则验证，失败以非零码退出
godot --headless --path . -- --uismoke       # 50 项界面/表现层验证，失败以非零码退出

# 3. 正常启动
godot --path .

# 4. 跳过菜单、用固定种子直接开局（调试用）
godot --path . -- --seed=123

# 5. 性能基线：跑 6 秒，打印首帧耗时 / 帧间隔分位数 / 节点数 / 托管堆
godot --path . -- --bench

# 6. 导出 PC 包
godot --headless --path . --export-release "Windows Desktop" build/win/AbyssEcho.exe
godot --headless --path . --export-release "Linux" build/linux/AbyssEcho.x86_64
```

CI 见根目录 `.cnb.yml` 的 `Godot 逻辑自检` / `导出 PC 包（Windows + Linux）` 两个 stage，
构建镜像在 `.ci/godot/Dockerfile`（Godot 4.7.2 .NET + dotnet 8 + 双平台模板 + Noto CJK 字体）。

**流水线本身踩过的五个坑**（都不在业务代码里，但会让 job 一步都跑不动）：

| 症状 | 根因 | 修法 |
|---|---|---|
| `mcr.microsoft.com/.../sdk:8.0-bookworm: not found` | 浮动标签已从 MCR 下架 | 固定到 `8.0.300-bookworm-slim`（同一个 Debian 12 base）；slim 缺的 curl/unzip/python3 本来就在 apt 列表里 |
| `"/install-godot.sh": not found` | build context 里只有 Dockerfile，脚本没被声明 | `by` 里列出要 COPY 的文件 |
| 加了 `by` 仍然 not found | `build: <路径>` 是字符串简写，旁边的 `by` 不被读 | 改成对象写法 `build: { dockerfile, by }` |

后两条一起才是完整的：`by` 决定「哪些文件进 context」，`COPY` 决定「从 context 的哪儿取」，
而只有对象写法才会读 `by`。

| 症状 | 根因 | 修法 |
|---|---|---|
| 自检打出 `38 通过 / 0 失败` 之后进程又挂十分钟，被 SIGKILL 判失败 | `GetTree().Quit()` 只是请求退出，待释放节点要等下一次树推进 | `Boot.QuitWithGuard`：照常 Quit，2 秒墙钟兜底硬退（`OS.Kill`，不是 `Environment.Exit`——Godot 的宿主没那个重载） |
| `--bench` 什么都没打出来就挂到超时 | 基准与帧采样器挂在 Boot 上，而 Boot 是主场景根节点，换场景就被释放；`await` 的续体跑在已释放节点上 | 新增 `Dev/BenchProbe`，挂在 root、不随场景销毁；用「时间片状态机 + 帧推进」而不是 async/await |

顺带：`--bench` 原来在 `_Ready` 里 `CallDeferred` 之后直接 `return`，**跳过了字体、主题与数据加载**，
量的其实是三个空场景。现在它走完整条初始化再开始计时。

本地实测（xvfb + llvmpipe）：`--bench` 7 秒跑完，采样 1857 帧，
首帧 432ms、帧间隔 p95 8.3ms、节点 59 / CanvasItem 54、托管堆 5MB。
导出之后还会拿**导出产物**再跑一遍 `--selfcheck` 与 `--uismoke`——
「编译通过」和「这个二进制能起来」是两件事。

## 6. 自检覆盖了什么

### 6.1 逻辑自检 `--selfcheck`（36 项）

`Scripts/Scenes/HeadlessSelfCheck.cs`，36 项，全部通过
（这不是「代码能跑」，而是「规则没被搬坏」）：

| 分组 | 验证的行为契约 |
|---|---|
| 随机数 | 同 seed 同序列；`Int` 落在闭区间 |
| 地图生成 | 房间数达标；全图连通；Boss 在最远点；保底事件房/商店各一个 |
| 场景可达性 | **每个房间都能从起点按方向键走到**（同一次 `Move` 与连线一致） |
| 伤害公式 | 最低 1 点；防御姿态减半；狭窄层 +15% 暴击**不依赖装备词条** |

### 6.4 第三批截图：敌人立绘位置、卡面材质、菜单辉光

这一轮的目标是「优化美术质量」，但开场先做了一件别的事：**把上一轮的结论重新量一遍**。
做法是在本机装 Godot 4.7.2 .NET + dotnet 8，跑 `--selfcheck`（26/26）与 `--uismoke`（38/38），
再 `--shot` 出四张截图，和 PR #69（那份改的是 **TS 侧** `src/ui/*.ts`，`godot/` 一行没动）逐条对照。

截图一开，发现一个**自检全绿但画面明显不对**的问题：

1. **敌人立绘被压在卡左上角，卡里空出一大片**。
   立绘的分辨率由「方盒的短边」决定，而卡里的槽位只有 132×94（卡高 150）——
   图形实际只画得出 70px，其余全是留白。上一轮的断言偏偏是「立绘不溢出槽位」，
   于是「立绘越小越安全」，测试绿了，画面坏了。
   根因还有一条更隐蔽的：`KeepSpritesInSlots()` 每帧按槽位高度重设立绘盒子，
   而 `Control.Size` 在布局跑完之前给的是高度 720 —— 它把 `CustomMinimumSize`
   写成了 124×720，槽位反而被撑成卡的高度。**那个方法是这一整类问题的坏源头，已删掉。**
   现在立绘挂在舞台层，尺寸由舞台高度定（普通 0.52、Boss 0.62，下限 96 / 上限 260），
   站位在舞台左侧，玩家立绘在右侧，两者成对角；卡只留出左边一窄条给它占位。
2. **卡面是一张纸**。`StyleBoxFlat.BgColor` 只给一个纯色，上下同色就没有厚度。
   补了 `Widgets.UnitCard`（自绘 `Control`）：8 段纵向渐变 + 上沿 1px 高光 + accent 淡染 + 圆角描边。
   顺带给 `Paint.RoundRect` 加了「四角半径可分别指定」的重载——切带子时首尾两条要跟着卡片圆角走，
   否则四个角会露成直角。
3. **菜单背景是一圈圈能数出来的年轮**。手画多层同心椭圆（TS 版也是这么写的）挡不住这种同心圆，
   纯几何叠色一定有台阶。改成 `GradientTexture2D` 的径向渐变纹理 + 一张 `TextureRect`，
   渐变本身连续，缩放无台阶。**这条的教训是：能交给渐变纹理画的，不要手工一圈圈叠。**
4. **地图格子被糊灰**。上一版在 `RoomIcon` 里叠了一层 0.55 alpha 的面板色当底板，
   而底板其实在 `Button` 的 `StyleBox` 上（它还负责悬停态与点击区），两层叠起来整块发灰。
   现在 `RoomIcon` 只画「地砖上的光」：外圈类型色晕 → 内圈压暗 → 上缘挑亮，做成圆形徽章。
5. **骑士是一块平涂蓝**。上一版是平涂 + 零散高光。现在照 TS 版那一版重写：
   所有面子统一「亮面朝左上、暗面朝右下」，披风褶皱、胸甲分片、肩甲与护颈、护鼻与翎羽逐层叠色阶。

`--uismoke` 的第 4 条断言也跟着改了：从「立绘在卡里且不溢出槽位」换成
「立绘盒子 ≥120px、落在视口内、顶边不压敌人卡、卡里留出了占位栏」。
断言写错方向的时候，绿是假的。

### 6.5 第四批：战斗舞台、地图徽章、主菜单、BGM、粒子池

起点和前几轮一样：`--selfcheck 26/26` + `--uismoke 38/38` 全绿，装好 Godot 4.7.2 .NET + dotnet 8 +
xvfb 截图之后，四屏逐张看，问题一片。**绿灯和「能用」之间隔着的就是这一节。**

### 战斗界面

1. **骑士被画面下沿裁掉半截**。舞台地板线 `StageBottom` 被算成「行动条顶边」——那是舞台的**底界**，
   不是立绘的**站位线**。640 高窗口下 `StageBottom(570) < StageTop(580)`，舞台高度是负数，
   立绘用这个负数推坐标就跑到卡上面去了。
   现在 `Compute` 显式返回 `StageTopY` / `StageBottomY`，地板线 = 底界 − `StageFloorInset`，
   并夹在 `[StageTop + StageTopSpacing, 底界]` 之间。**任何视口高度下舞台高度都为正**，这条进了断言。
2. **两个立绘都往下偏了半个身位**。`HeroSprite` 用 `Size*0.5` 当绘制中心，而骑士是
   「头顶 −37、靴底 +26」——中心不在框中心。`MonsterSprite` 同理（图形只占框高 2/3）。
   两处都改成「脚踩框底」，于是地图、战斗共用同一套站位。
3. **战斗界面里有两个「你」**。行动条血条前钉着一个 40px 小骑士，舞台右上是 240px 的大骑士。
   同一屏出现两个自己，玩家会以为那是队友。行动条那个删掉，立绘只留舞台那一个。
4. **血量数字被挤到屏幕外**。血条是 `ExpandFill`，把 `60/60` 压成半个字。
   给数字一个不缩的 96px 最小宽度，同时把状态图标行改成 `ShrinkEnd`。
5. **日志面板是一块空黑条**。截图工具不推进回合，所以第一屏日志只有一行。
   `--shot` 现在会先让 AI 打两回合（走和按钮完全相同的 `Act` 入口），日志着色、飘字、受击后仰都会真的发生。
6. **敌人卡里那块空白**不是漏画——原版 `createFighterPanel` 就在这里留了立绘位。补上
   `EnemySocket`（凹陷底衬 + accent 描边 + 四角十字），空位现在读作「立绘位」，不是「没画完」。
7. **立绘不会动**。加了 `Lunge()` / `Recoil()`：出手前冲、挨打后仰，两方向相反；
   受击闪白也补给了玩家侧。方向对错进了断言（`LungesForward`）。

### 地图界面

8. **网格贴在右边，左边一大片空**。`RoomCenter` 按声明的 `Width/Height` 居中，
   而生成器只在中间一片撒点：声明的 7 列里往往只用掉 4 列。改成按**房间实际包围盒**居中。
   > 这条以前的断言是「左/右留白都 > 0」——332 / 608 两个数都是正的，于是它一直是绿的。
   > 现在判「左右留白之差 < 一格」。
9. **地图上的骑士顶出房间格**。给的是 48×64 的框 + `SetHeroScale(0.66)`，
   而 0.66 倍的骑士只有 38px 高，人挤在框的下半截。改成 40×44 的框，位置按「脚对齐格底」算。
10. **房间格上扣着半块暗色饼**。罪魁是 `Paint.Arc`——它把圆心塞进顶点表当第一个点，
    画出来是**实心扇区**而不是弧。房间徽章的「上缘挑亮」用了半透明色，于是整块半圆盖住图标。
    现在 `Arc` 只描线，扇形另开一个 `Sector`（圆角矩形的角要用它）。**一个函数名两种语义就是这次最大的坑。**
11. **剑图标是一根白钩子**。刃画成从 `(-1.5,-13)` 到 `(2.5,8)` 的细三角，缩到 37px 宽不到 1px。
    重画整把剑：对称刃 + 剑脊高光 + 护手 + 柄 + 柄头。
12. **色晕是一枚浅灰圆盘**。格子里垫实心圆，深色底上就显成盘子。新增 `Paint.Ring`，只留一圈环。

### 主菜单（这一屏之前基本没移植）

13. **只有一行白标题**。原版是 `makeWordmark`：每字一块带底光的小方牌、奇偶错位 ±4px，
    两侧剑与骷髅、外加 26 粒漂浮尘埃。全部补上（`UI/MenuDeco.cs`）。
    - 字标排版是纯函数 `WordmarkLayout`，断言「相邻牌不重叠」「奇偶错位」「总宽装得下四个字」
    - 装饰位置判据是**牌子的占用区**而不是控件框：控件左右各留半块牌，装饰落在留白里看着仍像压在字上
    - 下划线画在 `Wordmark` 内部：单独放一个 `Control` 进 `CenterContainer` 时，
      拿到的 `Size` 一直是 0，线一次都没画出来（试了三轮容器写法都不行）

### BGM（从「垫子」变成「曲子」）

14. **每段曲子只有根音 + 五度 + 一次琶音**，所有楼层是同一块垫子换调——「有 BGM」不等于「有曲子」。
    重写合成器，三层都按谱走：
    - **贝斯**：i–VI–III–VII 四和弦进行，每两拍换根音，换根音时带短包络
    - **旋律**：`BgmDef.Motif`（音阶级数，-1 为休止）× `BgmDef.Scale`（小调/和声小调/多利亚/弗里吉亚/利底亚/五声），
      带 ADSR 包络与 12 音分滑音；每段曲子有自己的音阶与动机
    - **空间**：高通白噪，音量跟亮度走
    - 长度从 2s 提到 8s（一个完整乐句）
15. **循环点有爆音**。上一版末尾与开头做线性交叉淡化，结果末采样 = 首采样，
    数值相等但**斜率**断了，实测跳变 0.316。改成「末段用 smoothstep 收敛到 `buf[0]`」。
    断言直接查 `|buf[0] - buf[^1]| < 0.05`。

### 粒子

16. **批量到期是 O(n²)**。倒序 `RemoveAt(i)` 每删一个都要搬后面的元素；一次冰霜新星 36 颗 +
    石肤 20 颗同帧到期就是几百次搬动。改成「先标死、再一遍紧致化」，容量一次扩到 `MaxParticles` 不再扩容。
    断言：容量封顶、同屏不超限、全部过期后回收干净。

的三层描边折线、接缝处有门框、可走方向在走廊中点跳动、未探索房间是「? + 一圈虚线」、
右下角还有一张十一行的类型图例。Godot 版当时是 `Button + StyleBox + RoomIcon`：

1. **走廊是一条 2px 直线**，十三个房间看起来像电路图。改成 `UI/MapLines`：
   三层描边做厚度、先横后竖、接缝补门框、只连「至少一端已探索」的房间（迷雾感靠这个）。
2. **房间砖没有砖缝、没有厚度**。底板在 `StyleBox` 上、图标是子节点，两层圆角对不齐，
   深色底上整块发灰。改成 `UI/RoomTile` 一个 `_Draw` 画完：厚度层 → 砖缝 → 徽章环 →
   图标 → 起点标签 / 清空勾。
3. **未探索的房间只显示一个灰色问号**。补上「剪影 + 一点类型色 + 呼吸的问号」。
4. **没有图例**。玩家只能靠图标猜「那个货摊是不是商店」。补 `UI/MapLegend`，
   十一行按颜色分类，**矮窗口折成两列**（1024×576 下竖排会把末行挤出面板）。
5. **地图是一张小图漂在大屏中间**。这是最刺眼的一条：格距写死 92，而生成器只撒在
   包围盒里，1280 宽下画幅 450px，两边各空 400 多。改成 `UI/MapMetrics.Fit`：
   按「可用区域 − 图例那条竖带」反算格距，上限是设计值 92、下限 44。
   > 断言写的是**画幅占比**（`Coverage`）与「格距至少到可用区域算出来的那个数」，
   > 而且断言里传的是生产常量（`MapScene.HudBandHeight`、`MapMetrics` 的默认参数）。
   > 第一版把 92 写成字面量，把上限改成 60 也照样绿——**断言和被断言的东西必须是同一份数据**。
6. **地图压到图例上**。居中不能再用「左右留白相等」：右下角有一条竖带被图例占了。
   现在 Fit 显式接收 `reservedRight`，断言改成「在除掉图例的区域里居中」+「不压图例」+「图例不出视口」。
7. **图例面板比内容矮一行**。表头高度被算了两次（一次进 `HeightFor`，一次又被减掉），
   末行「空房间」被裁在面板外，看着像图例少了一项。断言直接引用 `NeededHeight`。

#### 战斗舞台：怪比人小，人比怪大

8. **屏幕上出现一个巨人骑士**。上一版玩家立绘按「0.86 × 舞台高」当**盒子**高度，
   而骑士本体只占盒子的一部分，于是 240px 的骑士站在屏幕上，怪只有 300px 的盒子里那点图形。
   现在玩家立绘只出现一次，在**行动条的血条行里**（原版 `createFighterPanel` 的位置），
   尺寸跟行高走、比例按本体（34 : 58）。舞台上不再站人——玩家打上去的伤害飘字落点是
   算出来的「他的站位」，不是某个控件。
9. **怪物比骑士小一圈**。根因是两套账：`PlaceSprites` 用 `size × 1.4 / 1.5` 定盒子，
   而 `MonsterSprite._Draw` 只把框的 `1/1.5` 当图形。现在两边写同一对常量
   （1.12 / 1.32），并且 `MonsterSprite.SizeFromParent` 让 `Setup` 别改尺寸。
   **一个尺寸在两个地方各算一遍，迟早对不上**——这条和「Arc 既画弧又画扇」是同一类错误。
10. **骑士被横向压扁成蓝团子**。地图上那个 `40×44` 的窄盒子 + `0.62` 的比例尺，
    和战斗里那个「宽 = 高 × 0.72」的盒子，都是同一件事：`HeroSprite` 的绘制原点在脚底，
    缩放是「设计高 58 → 像素」，盒子必须按 34 : 65（含投影）反推。

#### 顺带

11. **截图工具自己撒谎**。`--shot` 拍地图时只走过起点房，满屏问号——
    看起来像「迷雾做坏了」，其实玩家正常玩几步就是这样。现在截图前沿 BFS 把前七间
    标成已探索；这不是改游戏，是让证据对得上「玩家会看到的画面」。

这一轮的断言：`--uismoke` 43 → 44（新增「地图画幅撑得起来」一条，内含格距下限与上限两条判据），
外加改写了三条（房间砖、玩家立绘位置、图例装得下）。**每条新断言都反验过**：
把格距上限压回 60、把图例高度减掉表头，断言立刻变红，改回来立刻绿。

### 6.8 这一轮：绿了但结论是假的

起点是「往后主要维护 Godot 版」，于是先不相信任何一行「全绿」，把每一条结论重新量了一遍。

#### 自检里两条结论是假的

1. **「40 局自动游玩 0 胜 / 2 负」这句话本身就是症状**。自检里遇到战斗房是

   ```csharp
   if (!won) { game.OnBattleLost(); break; }   // 现在的写法
   // 以前：`break` 出去，再由外层 Advance 推一步
   ```

   更早的版本连 `-- uismoke` 都没有的时候，模拟器干脆**假定每场都赢**：
   一路 `OnBattleWon(...)`，于是 40 局从来没死过人，「与 TS 版结论一致」这句是照着 TS 的数字抄的。
   这一轮把模拟器改成真的会玩：会喝药、会换更强的装备、会付不起就不买、
   会在残血时撤退、会按「付不付得起」挑事件分支。**随机操作 0/40 胜、最深第 10 层；
   理性操作 0/40 胜、最深第 15 层（正好摸到最终 Boss 那一层）。**
   两条断言互为一对：随机必须 0 胜（难度没被调空），理性必须走到第 5 层以上（成长曲线没断）。

2. **「地图上有去不了的地方」是真的**。修完模拟器才发现 36/40 局在 4000 步上限上打转。
   根因不在游戏，在模拟器的寻路：它只看**当前房间的相邻格**挑「未访问」的那个——
   走到一个所有邻居都去过的格子上，就再也走不出来（树形地图上必然发生）。
   改成全图 BFS 找最近目标、沿最短路走一格之后，40 局全部正常推进。

3. **成就从来没落过盘**。`OnBattleWon` 里是 `Meta = MetaProgression.GrantAchievement(...)`——
   只改了内存，没走 `MetaSaver`。碎片走了 saver、成就没走，同一条链路的两种待遇：
   「击败逆位 Boss」这条成就回标题就没了。现在统一成 `Game.GrantAchievement(id)`，和碎片一样落盘。

#### 截图抓到的（自检不可能发现）

4. **骑士被「投影」撑高了 1.12 倍**。`HeroArt` 的绘制坐标从头顶 −37 到脚下投影 +22，
   而三处换算各自用 `DesignHeight = 58` 当分母。少算那 22 像素的投影，比例尺就放大 1.12 倍：
   地图上头盔压住上一块地砖，战斗里行动条的立绘顶出格子。现在统一成 `HeroArt.LayoutHeight = 65`。
5. **屏上的怪比骑士还小**。敌人立绘的盒子是 `设计直径 × 1.12 × 1.32`，
   而 `MonsterSprite` 只把框的一部分当图形——两套余量对不上，720 高下普通怪的盒子只有 234px。
   现在盒高由舞台高直接给（普通 0.78、Boss 0.98），比例照本体 34 : 65。
6. **放大立绘把按钮行挤出了屏幕**。血条行是固定高（56），里面塞了 96px 的立绘，
   多出来的高度由容器从下面的按钮行里扣——截图里「攻击(A)/防御(D)」只剩上半截。
   现在立绘预算来自 `HpRowHeight`（`BattleLayout.HpRowBudget`），
   并且加了一条断言：「立绘预算 ≤ 血条行高」+「行动条配额 ≥ 内容高」。
   **这条和 6.3 第 1 条是同一个坑的第二次复发**，所以这次把它写成了预算关系而不是一个数。
7. **地图右下角的图例压着最后两列房间**。`Fit` 里的 `reservedRight` 只用来居中，
   没从「可用宽」里扣——同一件事漏算了一头。现在两处都扣。
8. **底部提示条第一个字被切掉**。提示条贴着左边缘，没有内边距。补了 16px。
9. **图例表头「? = 未探索」压在上边框上**。字号 11 的字基线写成了 `PadY + HeadH*0.4 - 3 ≈ 12.4`，
   正好落在描边线上。改成 `PadY + 11`。

#### 退出路径上的一个真 bug

10. **自检全绿之后进程以 134 退出**。`Boot.QuitWithGuard` 的兜底线程里调了 `OS.GetProcessId()`——
    Godot 的托管宿主是线程绑定的，后台线程碰 OS 单例会直接 abort
    （`Object name: 'Godot.OSInstance'`）。以前日志里看不出问题，CI 却把一次成功的自检判成失败。
    现在进程号在**主线程**上取好，再交给兜底线程只用那个整数。

### 6.9 第六轮：翻译偏差、日志空转、地图画幅

这一轮不是「再加一点内容」，而是**拿 TS 版当标尺逐条对**，加上重新看四张截图。
前提照旧：`--selfcheck` 与 `--uismoke` 全绿，装好 Godot 4.7.2 .NET + dotnet 8 + xvfb 之后逐张看图。

#### 翻译偏差（TS 版有的，这里没有）

1. **`FixedDamage` 少了 `Math.Round`**。TS 版 `fixedDamage` 是 `Math.max(1, Math.round(amount))`，
   C# 版写成 `Math.Max(1, amount)` —— 形参是 `int`，但调用方可以传小数
   （楼层机制里的反震 `5.5`），`(int)` 隐式截断成 5。两边算出不同的数，还查不出是谁改的。
   现在两处都按「先四舍五入、再夹下限」结算。
2. **`SwapInItem` 丢了返回值语义**。文档注释写着「丢弃 + 入手必须一起成功」，
   实现却只是 `ReplaceItem` 的一层包装——被丢掉的那件没返回，界面没法写「你失去了 X」。
3. **`GameDataStore.Validate` 只搬了 TS 版的三分之一**。`loader.validate` 里关于
   道具槽位 / 消耗品有效性 / 品质递增 / 词条引用 / 诅咒房词条池 / 精英房倍率 /
   元进展碎片表 / 血祭代价 / 敌人成长率 / 敌人 AI 概率和 / 升级曲线的那几十条，
   移植时整段漏了。后果不是崩溃，而是**静默失效**：槽位写错的道具「怎么点都装不上」，
   词条 id 打错的装备「莫名少一条」。现在全部补齐，并加了一条自检用例
   「故意写坏配置 → 启动必须报错」，把「以后改错了会立刻红」也钉住。

#### 存档链路

4. **运行时装备的 id 会撞上已登记的那件**。诅咒装 / 附魔装 / 精英附词条装的 id 形如
   `<底板>_r<N>`，`N` 是 `Game` 的一个内存字段。读档把历史装备按原 id 塞回 `ItemIndex`，
   而计数器在新 `Game` 里从 0 开始——只要二者没对齐，新生成的那件就会叫 `_r1`，
   把背包里那件的定义整个盖掉（玩家身上的紫装被换成刚掉落的那件，两件同名不同物）。
   现在 `NextRuntimeItemId` 分配时先查占用，`RestoreRuntimeItem` 顺手把计数器推到已用过的最大值。

#### 战斗界面

5. **日志面板永远是满高的**。它固定 96px：开战第一屏只有「遭遇 巨鼠！」一行，
   下面那块空白看起来像「日志没画完」，同时白白吃掉能放大立绘的一百多像素。
   现在面板高度 = `RichTextLabel` 实测内容高 + 内边距，上限仍是满高
   （日志再长也不许把按钮行顶下去）；省下来的高度直接算进 `LiveStageHeight`，
   立绘与站位跟着变大。面板一建好就 `CallDeferred` 同步一次——
   等 `Refresh` 再调就晚一帧，那一帧里容器已按满高排版完，高度再也收不回来。

#### 地图界面

6. **画幅只占可用区域的 61%**。旧 `Fit` 有两重留白（32 + 40）并且按 `cols` 整除，
   而网格实际宽度是 `(cols-1)×span + room`——差这 0.86 个格距就是一整列放不下、
   格距被迫收一档。现在按 `(cols - 0.14)` 反算，格距上限从固定 92 提到 132，
   5×4 的图在 1280×720 下能吃满 90% 的可用高度。
7. **图例在横屏下竖着吃一条宽**。旧判据是「1100×700 以上竖排」，1280×720 正好落在竖排那侧，
   于是图例独占右下 142px，地图宽度被切掉一截。改成「竖排会不会让地图变窄」判：
   只有宽度还剩 1200px 以上才竖排，否则折成两列贴底。
   这一轮之后，同一张 5×4 的图从 450px 画幅长到 642px。

#### 断言变化

`--selfcheck` 26 → 28（新增「运行时装备 id 不撞号」「非法配置一条都跑不掉」），
`--uismoke` 44 → 46（新增「日志面板跟着行数收」「地图画幅用满可用区域」）。
新增的两条都反验过：把修复改回错误版本，断言立刻红。
另外 `dotnet build` 的 1 条 `CS8604` 警告也清掉了，现在是 0 warning。

### 6.7 更早的截图抓到的真问题（第一轮）

`--shot=<目录>` 会在有显示设备的环境里（CI 里用 `xvfb-run`）把菜单/地图/战斗/Boss 出场各截一张图。**光看「自检全绿」是发现不了这些的**：

1. **战斗根节点尺寸是 0×0**。`Control` 的默认锚点是左上角单点，四条 offset 全 0 就等于 0 尺寸 —— 整个战斗界面缩在右上角一个看不见的点上。之前有 `SetAnchorsAndOffsetsPreset`，改手写 offset 时把它删掉了。
2. **容器把按钮拉成满宽**。`VBoxContainer` 不给 `SizeFlagsVertical` 就会吃满父面板的 262 高度，内部每一行被拉伸成一条，按钮和血条全贴到屏幕两边。
3. **弹窗面板是透明的**。`StyleBoxFlat` 的 `BgColor` 默认全透明，忘了写就只剩背后那层 0.62 黑的遮罩 —— 看起来像「弹窗没弹出来」。
4. **Boss 名字叠在左上角**。给 `Label` 手写 `Position` + `Size` 不可靠：字体的排版尺寸要等第一次布局后才算得出来，手写坐标会把标题和副标题压在一起。改成锚点容器 + 容器内对齐。
5. **主题挂晚了**。`Root.Theme` 必须在进场景之前挂；挂在某个场景自己的 `_Ready` 里，那个场景的根节点已经初始化完，界面就是一片空白。

## 6.10 这一轮：事件与存档链路上的六笔账

起点还是那句老话——「全绿」不等于「对了」。这一轮逐条核对**玩家能感知的三条链路**：
事件怎么结算、商店怎么记账、关窗之后还剩下什么。

### 事件结算

1. **事件给的装备把本层符文吞了**。训练房的「铭刻符文」承诺「本层下一件入手的装备多一条词条」，
   `Game.ApplyBonusAffix` 也确实实现了——但事件走的 `Events.ApplyEffect` 直接
   `player.Inventory[i] = gained.Id`，把模板 id 塞进背包：符文没挂上、也没被消耗，
   就躺在 `PendingBonusAffix` 里等下一次**战斗掉落**顺手吃掉。
   更隐蔽的是 id：模板 id 意味着背包里那件与模板共用同一份定义。
   现在 `EventApplyContext` 多了一个 `PrepareItem` 回调（`RandomItem` 与 `SwapItem` 都走它），
   界面与自检都传 `Game.ApplyBonusAffix`——「入手一件装备」只有一条路。
2. **事件付掉的金币没人记账**。商店扣钱一直记 `GoldLost`，事件选项（「投入 10 金币」）却只扣不记，
   于是结算面板上「金币获得」把花出去的也算成收入。现在 `Events` 对负值记 `GoldLost`，
   `MapScene.ResolveEvent` 记选项的 `Cost`。
3. **结果行的图标指错方向**。金币被画成 ✨ + 绿色，和「捡到东西」长得一样，
   「获得 -10 金币」更是读不通。现在金币走 `coin` + 金色，掉血才走 `skull` + 红色。

### 商店

4. **金币行永远显示旧余额**。它建在 `Render()` 外面，买完重建面板时那一行还是建面板那一刻的数。
   归 `Render()` 管之后，余额与「还差多少」才会跟着走。

### 存档

5. **地图上喝药不落盘**。存档存的是背包 id 列表，喝完药不写一遍，
   直接关窗（不走 Esc →「保存并回到标题」）就等于**把药退回来**。现在喝药与丢道具都立刻 `SaveRun()`。
6. **关窗就是丢进度**。`AutoAcceptQuit` 默认开着，关闭请求根本到不了任何游戏代码。
   现在 `GameStore` 在 `_Ready` 里关掉它，并在 `NotificationWMCloseRequest` 里先存档再退出——
   「只存可以被打断的安全点」这条规矩不变（战场仍然不存，回到敌人房重开一场）。

顺带两条同类的小账：`TryDescend` 的「继续深潜」分支没换 BGM、也没清本层苦练加成
（`ContinueDive` 换了新地图却不重置层内临时加成，上周目的 +15% 会跟着进新周目）。

### 1.9.0 发布红的那次：断言自己没跑起来

tag `1.9.0` 的「发布 Godot PC 版」在**自检阶段**就红了：逻辑自检 36/36 全过，界面冒烟 49 通过 / 1 失败，
失败行只有一句 `Exception has been thrown by the target of an invocation.`。

根因是上一轮新加的那条断言「地图上喝的药立刻落盘」自己写错了顺序：

```csharp
store4.NewRun(31415);
var run = store4.Run!;
...
store4.ClearRun();          // ← Run 被置空，磁盘上的档也被删了
run.Player.Hp = ...;        // ← 改的是已经被丢掉的那一局
```

`ClearRun()` 把 `GameStore.Run` 置成 null 之后，`run` 只是一个没人认领的旧对象；
紧接着 `MapScene._Ready` 里的 `_run ??= _store.Run ?? _store.ContinueRun() ?? _store.NewRun()`
拿到的是一局全新的、背包为空的局，于是 `UseConsumable(0)` 去取 `Inventory[0]` 越界。
异常经过 `MethodInfo.Invoke` 被包成 `TargetInvocationException`，外层只打印 `e.Message`，
真正的越界信息被丢掉了——这也是为什么日志里只有一句没有信息量的英文。

修法两条：

- 清档必须在 `NewRun` **之前**（并给 `ClearRun` 补上「它会把 Run 置空」的文档注释，
  这类顺序坑下次还有人踩）；
- 这条断言改走 `StepAsync` 并等一帧再调私有入口：界面那一步的提示本来就要等地图场景铺完才建出来，
  时序靠运气绿着的断言迟早会翻。

### 7.1 存档链路修掉的 bug（都是真规则错误，不是观感）

那条挂了很久的「离线不推进游戏时间」查下去，根因不是断言写错，而是存档链路上的四个 bug：

1. **`Rng.Seed` 从来没被赋值**，永远是 0。存档里写的种子一直是 0，而读档靠它重算地图——
   于是「同一个种子长出同一张图」只在内存里成立，落盘之后就断了。
2. **随机状态没进存档**。只存种子的话，读档会把整个随机序列倒回开局：
   商店能反复刷、掉落的顺序可预测、战斗里的每一次判定都能被「读档」重抽。
   现在存 `rng_state`（内部状态，不是种子），读档接着上次的位置走。
3. **生成地图会推进主随机序列**。`RestoreFloor` 会重算整层地图，而重算吃的是主 Rng——
   读档这一刻就把接下来的掉落全改了。现在每一层用独立的 `MapRngFor(floor)`：
   地图只由「种子 + 楼层」决定，主序列一概不碰。
4. **商店货架没进存档**。读档后商店用新的随机位置重 roll，等于读档送一次换货。
   现在把已经打开过的货架连 `Sold` 一起存下来；恢复必须排在 `RestoreFloor` 之后，
   否则会被它顺手 `_shopCache.Clear()` 清掉。

顺带修掉的：

- **`uint32` 存读被当成有符号 32 位**。`ConfigFile` 从文本读回来的是 `Int`，
  随机状态高位为 1 时会变负数，直接强转就读坏了（表现为「读档后序列完全变样」）。
  现在统一按 64 位写、`AsInt64()` 取、`unchecked` 截回 `uint`。
- **三 Boss 连战读档会退回第一只**。队列以前靠「第一次进房」这个隐式时机建，
  读档后内存里没有队列，于是重排回熔岩领主。现在按楼层重建队列，并把 `gauntlet_index` 入档。
  连战中途打倒一只也立刻落盘，且不弹奖励、不刷房间。
- **BGM 的「Boss 层」参数传的是「最终层」**，于是第 1~24 层永远当不成 Boss 层；
  打完战斗回地图也没把战斗曲换回来。现在按 `BossStage(floor)` 判，回地图统一走 `EnsureFloorMusic()`。
- **13 种楼层机制里只有 6 种配了曲子**，其余静默退回默认垫底——第 4 层和第 1 层听起来一样。
  现在全量显式配；断言也从「曲子存在」升级成「每种机制都必须显式配过」。
- **Boss 自己的机制从来没上过界面**。战斗左上角只画「本层机制」，玩家只看到 Boss 突然打多了一截，
  无处可查。现在 Boss 机制与周期（每 N 回合）一并显示，连战标题带 `连战 2/3`。
- **空格等待写在键位表里但没接**（TS 版有）。现在接上了，只报当前处境，不改任何规则。
- **弹窗开着时 Esc / H 一起失灵**。键位表写着「Esc 关闭面板」，实际被 `_modal` 判在前面拦掉。
- **训练房符文会被消耗品吃掉**：`Rewards` 对掉落的消耗品也会 `ApplyBonusAffix`，
  符文刻在一瓶药水上，玩家什么也得不到。
- **矮窗口下敌人卡不收**：行动条收了 60px，卡还是 108，舞台被挤掉，立绘与飘字压在血条上。
  现在卡高也进 `BattleLayout`（先收卡、再让舞台保底 150px）。
- **`--bench` 在真 headless 下会挂住**：`SceneTreeTimer` 靠帧推进，没有渲染帧就永远不触发，
  进程一直等到被外面杀掉（CI 里表现为「静默超时」）。现在先判显示驱动：headless 直接说明「量不了」并以码 2 退出；
  有设备时另有 20 秒墙钟兜底，收尾必须 `CallDeferred` 回主线程（定时器回调在线程池线程上碰 Node 会炸）。

断言变化：逻辑自检 19 → 23 → 26，界面冒烟 25 → 29 → 32 → 38 → 43 → 44。新增的都是纯数据/纯函数断言——
货架往返、随机状态不回退、连战读档不倒退、苦练不跨层、符文不吃消耗品、
敌人卡不压行动条、每只连战 Boss 机制不同、每种机制都配了曲。

### 7.2 规则层的 bug（也是真的错）

1. **首杀碎片能刷**。`_beatenBossFloors` 只在内存里：读档后集合是空的，玩家回到同一层 Boss 房再打一次，
   碎片又发一遍。现在它进存档（`beaten_boss_floors`），存档版本因此升到 **v2**。
2. **BGM 判 Boss 层用的是「是不是最终层」**。第 25 层是三 Boss 连战、第 30 层才是最终层，
   于是连战全程放的都是普通层垫底。现在统一走 `Game.IsBossFloor`（有没有 Boss 机制），
   地图与战斗两侧共用一个判据。
3. **进战斗不换曲子**。`BattleScene` 里根本没有调过 `Sfx.Music`，只有回地图时换——进战斗和在地图上听的是同一段。
4. **训练房苦练进战斗就消失**。地图 HUD 上没有它的来源，战斗里也没有任何地方读它，
   玩家看到的是「选了苦练，伤害没变」。现在 HUD 与战斗状态行都写明「苦练 +15%」。
5. **`affixesOwner` 传成了施法者**（TS 版是 `actor`，C# 版照抄了那个写法）。
   注释写的是「只有玩家的治疗会被贪婪之刃削弱」，代码判的却是 `ctx.Actor == ctx.AffixesOwner`，
   这个条件对双方都成立——敌人的暗愈也会被玩家的诅咒削一半。现在传玩家。
6. **状态图标行会凭空占位**。空列表时把 `Size` 写成 1×22 而不是 0，
   容器就永远给它留一行——行动条白高 22px，日志与按钮被往下挤。

截图抓到的布局问题另见 6.3（舞台、立绘站位、日志半屏空条、状态行 1px、敌人卡贴边）。

### 7.3 截图 + 逐条对照 TS 版抓到的

这一轮的起点是「再看一眼截图」，和逐文件对照 TS 版。两条路各抓出一批。

**截图抓到的（自检全绿也发现不了）**

1. **按钮行被挤出屏幕**。行动条配额 232，内容实际要 250：日志面板比自己那一行文字高 10px
   （面板内边距），血条行里塞了个 56px 的立绘。差值恰好等于「按钮只露出上半截」。
   修法不是把 232 改大——那样下次加一行又要错——而是把**内容高度做成布局的常量**
   （`ActionBarChrome` + `LogPanelHeight`），配额由它加出来，并加一条断言
   「配额 ≥ 内容高，且 720 下设计值**等于**内容高」。改内容忘改配额，这条会红。
2. **敌人立绘溢出卡片**。`MonsterSprite` 的盒子是 `size×1.4 × size×1.5`，
   而卡里只留了 `size`——立绘向下溢出，把名字行顶到卡外。现在盒子由**槽位实际高度**
   决定（`FitEnemySpriteTo`，每帧核对一次，因为容器布局要几帧才稳定），
   图形尺寸也从控件框反推，不再用 Setup 时的旧 `_size`。
3. **敌人卡的内容从来没被算进高度**。卡高写 118，六行内容 + 上下内边距实际要 150。
   多出来的 32px 从舞台里扣，立绘与机制横幅就压在一起。现在 `EnemyPanelHeight`
   = 内容 132 + 内边距 18，并且随窗口按比例收（下限 84）。
4. **零散的硬编码坐标**。机制横幅写死 `y=112`（矮窗口下压进卡里）、
   组合小卡写死 `x=24`（压在立绘上）。都改成读布局。

**逐条对照 TS 版抓到的（都是「原版有、这里没有」）**

5. **事件「用一件道具换一件未知的」少了挑道具那一步**。TS 版是 `showSwapPicker`，
   Godot 版直接随机换掉背包里一件——玩家既不知道自己交出了什么，也看不到那张卡。
   现在先弹选卡面板，玩家挑中的那件才会被换走。
6. **换完还多问一次「背包满了要放下什么」**。`SwapItem` 是原地替换，背包大小不变，
   但 `ApplyEffect` 给它带了 `NeedDiscard`，于是挑完道具又被要求丢一件（其实没满）。
   现在 `SwapItem` 不带 `NeedDiscard`；`NeedDiscard` 只在「拿到的东西真放不进背包」时出现。
7. **没有新手引导**。TS 版第一次开局讲一次「品质 = 词条数」——这是整个构筑的核心，
   而 Godot 版一个字的说明都没有，玩家只会按攻击力挑装备。现在补了这张卡，
   标记跟着存档走（`GameStore.IntroSeen`），不占元进展的存档位。
8. **战斗里缺 `V` 特效开关**（TS 版有）。补上，并且是持久化偏好
   （`GameStore.FxEnabled`），关掉只影响粒子/飘字/屏震，结算与日志一条不动。
9. **战斗里缺 `Z` 消耗品快捷键**。键位表写着「Z 使用消耗品」，而上一版只有鼠标能点。
   现在 Z 与按钮走同一个入口（`UseConsumableAt`）。
10. **战斗里的 `H` 说明面板没接**（MapScene 接了，BattleScene 没有）。
11. **玩家状态行不报「敌人中毒 N 回合」**。毒雾这类技能的收益只有玩家自己知道，
    不写出来就分不清「我放了毒」和「我什么都没做」。TS 版 `refreshBuffRow` 同时报双方。
12. **地图上没有浮动提示，只有一条会被覆盖的 Label**。TS 版有一条会淡出、会排队的
    toast，且同一条消息有节流（长按方向键会以几十次/秒重发 keydown）。
    现在 `UI/ToastRules`（纯函数）+ `UI/ToastLayer`，队列与节流都能断言。
13. **面板里没有图标**。TS 版的升级、奖励、祭坛、训练房、诅咒房、事件结果、背包、商店
    都配了矢量符号，Godot 版全是一行行文字。补了 `UI/IconView` + `Widgets.IconRow`，
    造型还是 `IconArt` 现画，不引入任何贴图。

**顺带修的**

- 地图上喝药：满血时喝、以及在没有中毒时喝解毒剂，会把药浪费掉。现在不消耗并说明原因
  （TS 版同一条：`if (!had) return`）。
- 祭坛献祭后当前血量没按**结算后的**上限收口：血条会显示 60/50，读档时才被存档的夹取「修好」。
- `BattleLayout` 里「舞台至少 150」这条常量没被断言用上（断言写死了 200）；
  现在断言直接引用常量，改常量不用改两处。

## 8. 后续路线（macOS / Linux / Steam / 自动更新）

- **macOS**：装 macOS 导出模板 + `codesign`（Apple Developer 证书）；`.app` 打包用 `export-release "macOS"`。
- **Linux**：已经出了 `tar.gz`；要更友好的分发可加 `.AppImage`（appimagetool）或 Flatpak。
- **Steam**：用 `GodotSteam`（GDExtension）接 Steamworks；成就直接映射现有 `achievements` 字段。
- **自动更新**：Godot 没有内置更新器。两个方向：
  ① 外挂一个轻量更新器（比对 manifest + 下载 pck 热替换）；
  ② 走 Steam / itch 的渠道更新。
- **体积与启动**：当前 Windows 包 ~70MB（zip），主要开销是 .NET 运行时与 Godot 导出模板。
  若继续压缩，可评估 **NativeAOT**（Godot 4.7 对 AOT 支持仍在演进）或裁剪程序集。

| 更小、更快、更省资源 | ✅ **同机实测过了**（见第 10 节）：包体 Windows 70MB vs Electron 111MB（−37%），Linux 60MB vs 99MB（−39%）；到首个可交互画面 485ms vs 1699ms（**快 3.5 倍**）；常驻内存 585MB vs 9MB 托管堆（整个进程约 60MB） |

**结论**：规则层与表现层都搬完了，而且都在自动化验证之下（36 项逻辑 + 50 项界面，全绿）。

这一轮补的是**验收线上的最后一格**：不再有一项标 🟡。「更小更快更省资源」从推测变成了同机并排的数字（第 10 节），
「玩家分不出是不是原版」这一轮的贡献不是「再画多一点」，而是**把四批截图里抓到的硬伤逐条修掉**——
战斗舞台几何（立绘被裁、两个「你」、血量数字出界）、地图居中与徽章（半块暗饼、白钩子剑、浅灰圆盘）、
主菜单（字标、装饰、尘埃、下划线之前整屏没移植）、BGM（垫子→曲子 + 循环点爆音）。

所有新修的规则都配了断言，而且每条断言都**反验过**：临时把修复改回错误版本，断言必须变红。
本轮反验过三条（舞台地板线、地图居中、立绘数量），都是改回原样立刻红、改回来立刻绿——
「绿了但没测」这种事只能靠这个办法排除。

## 10. 「更小、更快、更省资源」：同机实测

上一轮这一格标 🟡，理由是「两边都能量，但没有并排测过」。这一轮把两边都装上、
在**同一台机器、同一个镜像、同一个 xvfb 分辨率（1280×720）**下各跑三遍，取中位数。

### 10.1 包体

| | Godot 4.7 + C# | Electron 33 | 变化 |
|---|---:|---:|---|
| Windows 压缩包 | **70 MB**（zip：exe 105MB + pck 120KB + data 78MB） | **111 MB**（zip：win-unpacked 272MB） | −37% |
| Linux 压缩包 | **60 MB**（tar.gz：x86_64 71MB + pck 184KB + data） | **99 MB**（tar.gz：linux-unpacked 266MB） | −39% |

两边都是「可执行文件 + 资源」一起打，都没有额外压缩模板。
Godot 那份的大头是 .NET 运行时与导出模板；Electron 那份的大头是 Chromium。

### 10.2 启动到「可交互」

| 里程碑 | Godot | Electron |
|---|---:|---:|
| 进程启动 → 首帧 | **485 ms**（三次 463 / 485 / 491） | 没有「首帧」这个概念 |
| 进程启动 → 菜单可操作 | ~520 ms（首帧 + 一帧布局） | **1699 ms**（三次 1653 / 1654 / 1721） |

Electron 侧的里程碑是「`Menu` 场景激活且 `game.isRunning`」，和 Godot 的
「菜单场景 `_Ready` 完成」是同一件事。差 **3.5 倍**，主要差在 Chromium 的初始化
（进程模型 + GPU 进程 + V8 快照 + Phaser 引导）。

### 10.3 运行期

| 指标 | Godot | Electron |
|---|---:|---:|
| 帧间隔 p95 | 10.5 – 13.9 ms（约 72–95 fps） | 未单独测（Chromium 侧受 vsync 限制） |
| 场景对象数 | 59 个节点 / 54 个 CanvasItem | Phaser 对象 42 个（Container 5 / Graphics 31 / Text 6） |
| 常驻内存 | 托管堆 **9 MB**，整个进程约 **60 MB** | 多进程合计 RSS **585 MB** |

内存这一项差了一个数量级，原因很直接：Electron 要同时养 browser / renderer / GPU /
utility 四个进程，每个都带一份 V8；Godot 只有一个进程和一个 .NET 运行时。

> 测量方式：Godot 侧 `--bench`（`Dev/BenchProbe`，挂在 root 上不随场景销毁）；
> Electron 侧用一个只做测量的 `probe.cjs`，等 `Menu` 场景激活后读 `app.getAppMetrics()`。
> `--bench` 不进 CI 断言——CI 机器负载不稳定，**性能是趋势，不是阈值**。

### 10.4 复现

```bash
# Godot：三次取中位数
cd godot && for i in 1 2 3; do
  xvfb-run -a godot --path . --rendering-driver opengl3 -- --bench 2>&1 | grep -E "首帧|p95|节点数|静态内存"
done

# Electron：打包 + 测量（该版已移除，下面三条需从移除前的提交上检出才能重跑）
npm install && npm run build
npx electron-builder --linux --publish never
ELECTRON_DISABLE_SANDBOX=1 xvfb-run -a npx electron probe.cjs   # 打印 processToPlayingMs / rssMb / phaserObjects
```
